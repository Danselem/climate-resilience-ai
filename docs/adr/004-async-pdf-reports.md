# ADR-004 — PDF reports are asynchronous jobs with immutable artifacts

**Status:** proposed (not implemented; Phase 10)

## Context

Reports are required as PDFs. Rendering maps and laying out a document takes
15–35 seconds — far beyond a synchronous request budget — and the output is
something a planner will attach to a submission and cite months later.

## Decision

`POST /reports` writes a row to `report_job` with an idempotency key and
enqueues an SQS message. A worker using the same image renders static maps and
HTML, converts to PDF with WeasyPrint, stores it in S3, and records the status
and signed URL. Retries back off, then dead-letter. Concurrency is capped per
API key. The PDF embeds `run_id` and `mart_run_id`, and a sidecar JSON envelope
snapshot is stored beside it.

## Consequences

- Report generation cannot block the API and cannot be triggered repeatedly by
  one client without limit.
- A report is reproducible and diffable: given the same mart build it can be
  regenerated byte-for-byte, and if the mart changed the difference is visible.
- The 90-day S3 retention policy means old reports expire; the sidecar snapshot
  is what preserves the ability to regenerate them.
- Two services from one image, so a local queue shim is required to keep the
  local and cloud paths identical.
